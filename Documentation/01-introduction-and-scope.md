# Introduction and Scope

## Introduction

This document introduces the Altera® Sensor Link, an edge platform for deterministic ingestion, lightweight conditioning, and unified delivery of heterogeneous sensor data to a host over a high-speed Ethernet link using RoCEv2. The FPGA consolidates reliable sensor capture, optional hardware timestamping, format normalization, and edge pre-processing into a single device, providing the high-bandwidth, low-latency data path required for downstream processing on the host. Sensor sources such as cameras, lidar, radar, odometry, and IMU devices can be connected through dedicated FPGA resources, conditioned as required, and presented to the host as a coherent set of data streams.

The Sensor Link builds on Altera® IP and establishes capabilities in image signal processing, sensor ingestion, and high-speed networking. RoCEv2 carries InfiniBand-style transport over standard Ethernet and enables RDMA-based communication between the FPGA and host. In the Sensor Link, RoCEv2 is used to allow the host to consume sensor buffers with minimal copy overhead, supporting the bandwidth and latency requirements of multi-stream camera, lidar, and IMU data.

This release implements unidirectional data streaming using the Unreliable Connection (UC) transport from an Agilex™ 5 Modular Development Kit to a host over a 10 GbE link. The reference design provides five streams: two 1080p video streams at 30 frames per second, sourced from two Framos IMX678C sensors or generated by an internal test-pattern generator; one raw two-dimensional lidar data stream from an RPLIDAR A1M8 operating at approximately 5.5 Hz or generated by a test-pattern source; and two raw 64-bit streams from a Livox MID-360S (a point cloud at about 2.1 kHz with 96 points per reading, and IMU data at about 133 Hz), brought in by Ethernet Ingest. The two-dimensional lidar, the point cloud, and the IMU are forwarded without transformation. The video streams are assigned to RoCEv2 queue pairs 0x2 and 0x3, the two-dimensional lidar stream to queue pair 0x4, the Livox MID-360S point cloud to queue pair 0x5, and the IMU from that same lidar to queue pair 0x6. You can change these queue pairs with the Altera® Control Link over UDP provided in this release.

The design also associates captured sensor data with a common internal timestamp using the IEEE 1588 96-bit timestamp format. The timestamp is synchronized over PTP. A soft (fabric) implementation allows the FPGA global clock to synchronize to a host clock by exchanging PTP messages, which provides a common time reference for correlating data across the different sensor streams.

This release lets the host read and write any IP register in the FPGA using the Altera® Control Link library. It is a UDP-based protocol that provides non-RoCE communication between the host and the FPGA to configure the hardware in the FPGA design. The FPGA does not start streaming until the host has configured it with this mechanism.

The design is released as an SOF (SRAM Object File), which is the FPGA configuration image used to program the Agilex™ 5 device. Altera® retains the rights to the source code used to generate the SOF binaries. Because the included IP and system components have not reached the quality, validation, and hardening levels required for production deployment, this design is provided strictly as a reference design release and must not be represented or advertised as a production-ready solution.

## Scope

The architecture is shown in Figure 1 in the [Architecture](02-architecture.md) section. It combines the sensor-ingestion path and the UDP-based Altera® Control Link with Ethernet Ingest, PTP, a shared GTS reset, and five RoCEv2 channels.

### In scope

- Two MIPI camera inputs based on the IMX678C sensor and connected through Framos connectors.
- The MIPI0 input, corresponding to the first camera connection on the development kit, supports a Framos GMSL camera module. GMSL module support is limited to MIPI0 and is not supported on the MIPI1 input.
- One raw data stream from an RPLIDAR A1M8 two-dimensional lidar module. The lidar data is forwarded directly from the sensor without transformation; its format is defined in [Data Formats](07-data-formats.md).
- Lightweight image conditioning using ISP Lite, including conversion from the camera sensor's 4K, 12-bit Bayer output to 8-bit YUV 4:2:0 at 1080p and 30 frames per second.
- Data-format standardization across the supported sensor streams, as defined by Altera®, including RoCEv2-side chroma repacking from YUV 4:2:0 to an NV12-like format before Ethernet transmission.
- Unidirectional Unreliable Connection (UC) transmission over a 10 GbE link using Altera® OmniRoCEv2 IP. The RoCEv2 path is transmit-only from the FPGA to the host.
- Remote control, configuration, and initialization of the implemented FPGA IP, enabling UDP communication between the host and the FPGA over the Ethernet link.
- A hardware timestamping strategy that provides a common timestamp reference for captured sensor data, synchronized to the host via PTP.
- Ethernet Ingest for the Livox MID-360S 3D lidar and IMU. Each stream is 64 bits wide and is forwarded into the RoCEv2 subsystem.
- Five RoCEv2 channels. Channels 0 and 1 carry the camera streams, channel 2 carries lidar, and channels 3 and 4 carry the Ethernet Ingest streams (point cloud and IMU).
- IEEE 1588 PTP on the 10G Ethernet link, with the time-of-day value broadcast into the Ethernet MAC.

The supported sensor streams are ingested through dedicated FPGA resources. The camera streams are conditioned and standardized where applicable. The lidar stream and the two Ethernet ingest streams are forwarded as raw data. The streams are timestamped and transmitted to the host for downstream processing.

### Out of scope

The following capabilities are outside the scope of this release and may be considered for later development:

- Additional sensor types, including radar, external IMU, and odometry sources.
- Full image signal processing beyond the defined ISP Lite functions, as well as advanced analytics executed on the FPGA.
- Bidirectional or receive-side RoCEv2 data transport.
- Host-side sensor fusion, analytics, and application processing beyond receiving and interpreting the transmitted streams.

Future releases may extend sensor coverage, increase supported line rates, and introduce more advanced on-FPGA processing without changing the fundamental ingestion-and-transport model established in this release.
